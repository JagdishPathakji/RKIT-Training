////////////////////////////////////////////////////////
DEFERRED VS IMMEDIATE EXECUTION 
////////////////////////////////////////////////////////

-------------------------
what "DEFERRED" means ?
-------------------------
    var query = articles.Where(a => a.StatusId == 5);

At this line, NOTHING is executed. `query` is not a result. It is a stored PLAN: "when someone actually asks for values, loop through articles, and check StatusId == 5."

The plan only runs when something FORCES it to run. Things that force it:
- foreach loop
- .ToList(), .ToArray(), .ToDictionary()
- .Count(), .Sum(), .Any(), .First(), etc 


---------------------------------------------------
Methods that are lazy bs Methods that are immediate
---------------------------------------------------

LAZY (deferred) -- return IEnumerable<T>, build up the plan, run nothing yet:
    Where(), Select(), SelectMany(), OrderBy(), ThenBy(), Skip(), Take(), SkipWhile(), TakeWhile(), Distinct(), GroupBy(), Join(), Union(), Intersect(), Except(), etc...

IMMEDIATE (executes right away) -- returns a concrete value or collection:
    ToList(), ToArray(), ToDictionary(), ToHashSet(),
    Count(), Sum(), Average(), Min(), Max(),
    First(), FirstOrDefault(), Single(), SingleOrDefault(), Last(), LastOrDefault(), Any(), All(), Contains(),
    Aggregate()

Rule of thumb : if the return type is IEnumerable<T>,
it's lazy. If it returns anything else (int, bool, T, List<T>...), it
already had to run the loop to produce that value.



----------------------------------------------------
PITFALL 1 -- THE SOURCE CHANGES BEFORE YOU ENUMERATE
----------------------------------------------------
    
    var query = articles.Where(a => a.StatusId == 5);

    articles.Add(new Article { ArticleId = 99, Title = "New One", StatusId = 5 });

    var result = query.ToList();   // "New One" IS included!

Because `query` doesn't hold a snapshot of data — it holds a
REFERENCE to `articles` and a set of instructions. When `.ToList()`
finally runs the loop, it reads whatever is in `articles` AT THAT
MOMENT — including the item you added afterward.

This can be a bug OR a feature depending on your intent:
    - BUG if you expected `query` to represent "articles as they
      were at the time I wrote that line."
    - FEATURE if you actually wanted a "live view" that always
      reflects the current state of `articles` whenever enumerated.

If you want a frozen snapshot, force execution immediately:

    var query = articles.Where(a => a.StatusId == 5).ToList();  // snapshot NOW



----------------------------------------------------------------
PITFALL 2 -- MULTIPLE ENUMERATION (running the SAME query twice)
----------------------------------------------------------------
This is the most common real-world LINQ performance bug.

    IEnumerable<Article> query = articles.Where(a => a.StatusId == 5);

    int count = query.Count();          // runs the loop ONCE (to count)
    List<Article> list = query.ToList(); // runs the loop AGAIN (to build the list)

Two separate full passes over `articles`, because `query` is a lazy
recipe — every time you "ask" it for something, it re-runs from
scratch. For a small in-memory list this barely matters. But:

    - If `articles` were coming from a slow source (a database call
      wrapped in a custom IEnumerable, a network request, a big file
      being read line-by-line), this means DOING THE EXPENSIVE WORK
      TWICE.
    - If the underlying data can change between calls (like Pitfall 1),
      `count` and `list.Count` might not even MATCH, because the two
      enumerations could see different data.

THE FIX -- materialize ONCE, then reuse the materialized result:

    List<Article> list = articles.Where(a => a.StatusId == 5).ToList();  // runs ONCE
    int count = list.Count;              // just reads .Count property, no re-looping
    // reuse `list` everywhere else too, instead of re-querying `query`

General guideline: if you're going to use a query's results MORE THAN
ONCE, call `.ToList()` (or `.ToArray()`) on it first, and work with
that materialized collection from then on.



--------------------------------------------------------------
PITFALL 3 -- ACCIDENTALLY RE-RUNNING EXPENSIVE LOGIC IN A LOOP
--------------------------------------------------------------
    IEnumerable<Article> published = articles.Where(a => a.StatusId == 5);

    foreach (var article in published)
    {
        Console.WriteLine(article.Title);
    }

    // ... later in the same method ...

    foreach (var article in published)
    {
        Console.WriteLine(article.Title.ToUpper());
    }

Both `foreach` loops look fine individually, but each one causes a
FULL re-execution of the `Where()` filter over `articles`, from
scratch. If `Where()`'s condition involved something expensive (a
method call, a calculation), that expensive work happens TWICE.

Same fix as Pitfall 2 — materialize once:

    List<Article> published = articles.Where(a => a.StatusId == 5).ToList();

    foreach (var article in published) { ... }   // uses the stored list
    foreach (var article in published) { ... }   // uses the SAME stored list, no re-filtering



----------------------------------------------------------------------
PITFALL 4 -- CAPTURED VARIABLES CHANGE BEFORE ENUMERATION ("CLOSURE" TRAP)
-----------------------------------------------------------------------
This one is sneaky. Lambdas can "capture" variables from outside
themselves. If that outside variable changes BEFORE the query is
enumerated, the query sees the NEW value, not the value at the time
you wrote the line.

    int minStatus = 5;
    var query = articles.Where(a => a.StatusId >= minStatus);

    minStatus = 10;   // changed AFTER building the query, BEFORE running it

    var result = query.ToList();   // uses minStatus = 10, NOT 5!

Why? Because the lambda `a => a.StatusId >= minStatus` doesn't
capture the VALUE of `minStatus` at the time it was written — it
captures the VARIABLE itself. When the query finally runs (at
`.ToList()`), it reads whatever `minStatus` holds AT THAT MOMENT,
which is now `10`.

THE FIX -- if you need to "lock in" the current value, copy it into
a new local variable right before building the query, and don't
mutate that copy afterward:

    int minStatus = 5;
    int minStatusSnapshot = minStatus;             // freeze the value
    var query = articles.Where(a => a.StatusId >= minStatusSnapshot);

    minStatus = 10;   // no longer affects the query --
                       // query still uses minStatusSnapshot = 5
